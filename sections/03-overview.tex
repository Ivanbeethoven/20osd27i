\section{System Overview}
\label{sec:overview}

\subsection{State, metadata, and payloads}

\sys separates three decisions along the file-access path: which version
a task sees, how it retrieves immutable metadata, and how it stores and
fetches payloads. A lower reader resolves names, attributes, and data
locators under a fixed version identity. The data path returns the
referenced logical bytes using each object's persisted layout. These
interfaces allow metadata representation and object layout to change
without changing the file view.

Figure~\ref{fig:overview} maps the design to the following sections:
shared state and private changes (Section~\ref{sec:delta}), native or
packed metadata (Section~\ref{sec:packed}), and object formation
separated from backend layout (Section~\ref{sec:layout}). The mechanisms
are independently optional, so an ML experiment can mount a standalone
packed dataset beside a native writable workspace.

\subsection{Pinning a baseline}

A workspace binds a shared immutable lower and a private writable upper.
The lower supplies a fixed version through a sealed native layer or
a packed manifest. It may cover a selected subtree; the rest of the
source volume need not be frozen. Resolving every lookup through a
mutable latest-version pointer would violate this fixed starting view.

Private records determine which inherited names and ranges remain
visible. Section~\ref{sec:delta} gives the lookup and update rules;
merging independent edits requires an application protocol.

\subsection{One access, three boundaries}

Consider an agent that opens \code{config.json} in a shared dataset
and reads its first 4 KiB. Three decisions determine what that read
costs. The name is resolved against the workspace's private upper and,
if no private record exists there, against the lower; the lower answers
through a native catalog or through a joint page fetched from object
storage. The resulting record supplies a data
locator, and the client turns it into an object reference and a byte
range using the geometry in which that object was formed. The backend
finally reads and verifies the shard interval to which the range maps.

\subsection{Reads, writes, and publication}

An overwrite stores new bytes and publishes a private
mapping, leaving other workspaces' references intact. Buffered writes
can satisfy local reads before their objects become remotely durable.

Publishing a recoverable version requires durable referenced objects and
validated metadata. Ownership records retain metadata and payloads while
workspaces or readers still need them. Section~\ref{sec:implementation}
describes publication and runtime recovery.
