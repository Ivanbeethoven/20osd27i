\section{System Overview}
\label{sec:overview}

\subsection{State, metadata, and payloads}

\sys separates three decisions along the file-access path: which version
a task sees, how it retrieves immutable metadata, and how it stores and
fetches payloads. A lower reader resolves names, attributes, and data
locators under a fixed version identity. The data path returns the
referenced logical bytes using each object's persisted layout. These
interfaces allow metadata representation and object layout to change
without changing the file view.

Figure~\ref{fig:overview} maps the design to the following sections.
The upper region shows shared state and private changes
(Section~\ref{sec:delta}); the lower-left region shows native or packed
metadata (Section~\ref{sec:packed}). The lower-right region separates
object formation from backend layout (Section~\ref{sec:layout}).
The mechanisms are independently optional. For example, an ML experiment
can use a standalone packed dataset beside a native writable workspace.

\subsection{Pinning a baseline}

A workspace binds a shared immutable lower and a private writable upper.
The lower supplies a fixed version through a sealed native layer or
a packed manifest. It may cover a selected subtree; the rest of the
source volume need not be frozen. Resolving every lookup through a
mutable latest-version pointer would violate this fixed starting view.

Private names, attributes, deletion markers, and data mappings determine
which inherited records remain visible. Mutations leave the shared
baseline and other workspaces' private state unchanged.
Section~\ref{sec:delta} describes the rules for preserving inode identity,
updating names atomically, and preventing truncated bytes from reappearing.
Merging independent edits requires a separate application protocol.

\subsection{Reads, writes, and publication}

An inherited read obtains a locator from the lower reader and fetches
its payload range. An overwrite stores new bytes and publishes a private
mapping, leaving other workspaces' references intact. Buffered writes
can satisfy local reads before their objects become remotely durable.

Publishing a recoverable version requires durable referenced objects and
validated metadata. Ownership records retain metadata and payloads while
workspaces or readers still need them. A version can contain application
checkpoints, but restoring memory and open handles remains the runtime's
responsibility. Section~\ref{sec:implementation} describes the connected
publication and recovery paths.
