\section{System Overview}
\label{sec:overview}

\subsection{File views and storage interfaces}

\sys exposes file operations through a FUSE client backed by a metadata
service and object storage. An ordinary volume keeps its namespace in
mutable metadata. A workspace instead resolves private records over a
pinned immutable lower. Both views locate file bytes through data
mappings, allowing changes to a name or range to preserve references
to the remaining data.

Figure~\ref{fig:overview} shows where the three mechanisms act.
Delta-Based Workspaces compose the file view
(Section~\ref{sec:delta}). Packed Metadata supplies an alternative
representation for a selected read-only lower
(Section~\ref{sec:packed}). Variable-Granularity Object Storage governs
object formation and the BrewFS--RustFS layout interface
(Section~\ref{sec:layout}). An ordinary volume can use that interface,
and a packed version can be mounted directly for read-only access.

\subsection{Binding shared state}

A workspace binds a fixed lower version and a private writable upper.
The version may be a sealed native layer or a packed manifest covering
a selected subtree. Pinning that identity gives every inherited lookup
the same starting view even as other workspaces change or newer versions
are published. The private upper determines which names, attributes,
and byte ranges override that view.

The lower-query interface resolves names, attributes, and data locators.
Native metadata answers through the catalog; Packed Metadata answers
through authenticated indexes and joint pages. This interface separates
workspace isolation from the preparation of a packed representation.
An ML experiment can, for example, use a native writable workspace for
code and outputs while mounting a separately published training dataset.

\subsection{Reading and publishing data}

Consider a workspace reading the first 4 KiB of an inherited file.
Lookup checks private records and inheritance rules before consulting
the lower. A packed lookup returns the name, common attributes, and
data locator from a joint page. The data path follows the locator to
the stored bytes, using the representation in which those bytes were
written. RustFS translates the resulting object request into shard
reads under the object's persisted layout.

For new ordinary data, the client forms an object before requesting
a backend coding-block size. Our RustFS extensions support per-object
coding-block selection and finer shard verification, subject to backend
admission and compatibility checks. Persisting
the layout lets later reads and repair interpret an object independently
of the configuration used for subsequent writes.

An overwrite publishes a private mapping to new data while preserving
other workspaces' references. Publishing a recoverable version requires
durable objects and validated metadata; retention keeps referenced
objects live. Section~\ref{sec:delta} gives the update rules, and
Section~\ref{sec:implementation} describes writeback and recovery.
