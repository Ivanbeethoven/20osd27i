\section{Variable-Granularity Object Storage}
\label{sec:layout}

A file read names a logical byte range, but storage cost depends on the
objects containing it and the units fetched and verified. Large objects
can reduce request count for sequential access while increasing work
for a partial read. \sys separates client object formation from backend
encoding and verification. The finalized object connects these decisions:
its length is known after assembly, compression where applicable, and
framing.

\subsection{From file ranges to objects}

The ordinary data path maps file offsets to logical chunks and resolves
the visible slices within each chunk. A chunk is an addressing range;
slices identify the content supplying its visible intervals. The uploader
partitions a slice using client block size $g$ and addresses each block
by slice identity and block index. A 10 MiB slice with $g=4\MiB$,
for example, can produce raw blocks of 4, 4, and 2 MiB.

Compression and framing determine the finalized upload length $L_o$.
Thus $g$ partitions the slice, while $L_o$ measures the bytes uploaded.
Flush boundaries and partial writes affect object formation, and a tail
need not occupy a full block. Readers use the same geometry to translate
slice intervals into object references and offsets. Replacing one
interval can leave untouched intervals referencing older objects.

Chunk size must be a nonzero multiple of $g$. Because readers reconstruct
addresses from this geometry, changing $g$ for existing data requires
a compatible representation or migration. It is a configuration choice,
rather than a controller that adapts to observed access.

\subsection{Backend encoding and verification}

Once $L_o$ is known, the client can pass an optional encoding-block-size
hint to a compatible RustFS research backend. The hint requests backend
erasure-coding block size $B$ without changing $g$ or multipart part
sizes. The backend checks eligibility and compatibility, then persists
the effective $B$. Omitting a hint retains default selection.
Multipart initiation uses the complete object's length, and retries
retain that object's decision.

The interface accepts fixed hints of 64 KiB, 256 KiB, 1 MiB, and 4 MiB,
or a length-based policy. These choices apply to the formed object.
Section~\ref{sec:implementation} describes the current policy and its
relationship to the backend default.

The physical verification/read quantum $q$ determines how much shard
data is verified together. A separate backend policy can select
smaller units for eligible new framing. Full stripes must contain
a whole number of verification units per shard, with coding blocks
aligned across all data shards. Hint admission and new verification
framing have separate compatibility gates. Reads and repair use persisted
geometry even after write settings change.

\subsection{Physical work for a partial read}

Range GET can retrieve part of an object when the format permits
independent access. The ordinary store supports page-aligned range reads
for eligible small requests; compressed blocks or whole-object fetching
can require larger transfers. Packed frames provide a further decoding
and integrity boundary inside snapshot objects. Their size is distinct
from both $g$ and $q$. Caching and concurrent-read coalescing determine
which requests reach the backend.

The backend maps an object range to shard intervals and rounds each
interval outward to verification-unit boundaries. A 2 KiB shard read
at offset 3 KiB, for example, touches two 4 KiB units: 8 KiB plus
checksums, before tails or batching. Client fetching, compression, and
coding determine the shard interval. Smaller $q$ can reduce over-read
but adds checksum overhead. With unchanged data and parity shard counts,
nominal redundancy remains constant; a large $B$ does not imply a
fully padded tail stripe.

These layers require distinct measurements. Network read amplification
compares object-response bytes with application bytes served; physical
read amplification uses storage-device bytes as the numerator. Upload
amplification compares uploaded bytes with application bytes written.
Request count, compression work, and cache occupancy capture additional
costs. Compaction, retries, and short slices can increase upload work,
so smaller objects need not reduce write amplification.

A smaller backend quantum helps only if client fetching exposes
sufficiently small ranges. Snapshot producers and workspace upper writers
also have their own upload formats. The implementation differences below
determine which combinations can be compared without changing the
client path.
