\section{Packed Metadata}
\label{sec:packed}

\subsection{An optional representation for immutable state}

Packed metadata changes how fixed file-system records are stored and
retrieved. Its input is a selected source view containing directory entries,
attributes, and file-data mappings. Its output is a packed immutable
snapshot: authenticated records and access structures that describe the
selected subtree and locate its contents. Freezing these records permits
the reader to reuse their organization and validation across requests.

The same snapshot has two uses. An independent read-only mount serves it
directly through the file interface. A delta-based workspace
can instead bind it as its shared immutable lower, with private state
resolved by the workspace mechanism. Packed metadata therefore does not
require delta-based workspaces; a shared workspace baseline can likewise
use native catalog records. It also operates with the object backend's
default layout. These choices separate immutable access organization from
view composition and backend encoding.

\subsection{Freezing records into indexed, bounded units}

The organizing principle is to move work from repeated record lookup to
snapshot construction. The producer groups fixed records, encodes bounded
pages, and builds range indexes over their keys. A reader pins the manifest
identity and follows authenticated references to the required pages. The
index describes ordered metadata ranges; its height follows page capacity
and record count, independently of the source directory tree's depth.

In the current representation, a logical read group covers a parent
directory and a range of raw entry names in byte order. Its GroupMeta page
co-locates directory entries, common attributes, and file-data locators.
This organization lets a name lookup return information needed by later
attribute and data operations. The raw page is bounded at 256 KiB, while a
physical container may hold multiple groups. A group, a page, and an object
thus have different roles and sizes.

Metadata co-location, content inlining, compression, and data co-packing
are separate choices. Co-location combines related records; inlining puts
small file contents in a metadata page; compression changes the encoded
bytes; co-packing places multiple data regions in a container. Each can
change transferred bytes, decoding work, or cache use independently. The
layout comparison must distinguish their contributions.

\subsection{Fetching, verifying, and reusing records}

For \code{lookup(parent,name)}, the reader follows the directory-name index
to the group covering that key, resolves the container reference, and
fetches the GroupMeta byte range. It verifies the stored-byte digest before
decoding, then checks the resulting entry count and name boundaries against
the authenticated group reference. The requested record supplies the inode,
common attributes, and data locator. Figure~\ref{fig:packed} shows this path.

Other operations use the index appropriate to their input. Direct
\code{getattr} can obtain common attributes through an inode index.
Enumeration traverses ordered ranges, with counted indexes supporting
directory-ordinal navigation. A file read uses inline contents or resolves
a descriptor for the referenced data region, fetches the applicable range,
and verifies it. Packed data frames provide snapshot-level access and
integrity units; the backend interprets these object requests using its own
persisted layout.

Authenticated pages and resolved records can be cached under the pinned
snapshot identity. Immutability makes reuse valid for that identity without
tracking per-record updates. Bounded pages allow demand loading, but a cold
lookup may traverse several index pages, and a data read may need additional
descriptor and payload requests. Cache state and access locality therefore
affect both request count and useful bytes per fetch. Failed authentication
or a missing referenced object is an error, distinct from an authenticated
absence result.

For supported snapshot queries, these structures provide the required
namespace, attributes, and data locations without consulting per-file
records in the mutable metadata database. In a writable workspace, private
upper checks and control operations remain separate database traffic.
Cold-access tests must distinguish those requests from lower-record
lookups when establishing lower-query independence.

\subsection{Construction, publication, and reuse cost}

Construction fixes a source view, builds and uploads records and data
objects, and produces the indexed manifest. Source consistency requires a
snapshot or an explicit validation protocol. An immutable output alone
does not make a changing input atomic. Before publishing a new binding,
the selected protocol must establish that referenced dependencies are
durable and valid. Producing a manifest and publishing its reference are
separate events. Existing readers retain their pinned view until its
objects can safely be reclaimed; ordinary file close does not rebuild it.

The current concrete format uses PM11 manifests, IP06 indexes, and GroupMeta
pages. It instantiates the frozen-record and indexed-fetch principles with
directory-oriented joint records. Earlier tree-and-batch formats express
the same organizing principle through different record and wire layouts;
their compatibility and mount support are implementation properties.

Construction, validation, publication, rebuilding, and reclamation all enter
the cost comparison. For each additive resource metric $c$, we will measure
\begin{equation}
C_c(K)=C_{c,\mathrm{build}}+C_{c,\mathrm{publish}}
       +\sum_{i=1}^{K}C_{c,i}+C_{c,\mathrm{reclaim}}.
\end{equation}
CPU-seconds, transferred bytes, and monetary cost are separate metrics;
concurrent task wall-clock times are not summed into a batch makespan.
Reuse pays for construction only when the accumulated access savings exceed
these costs. Frequent rebuilding, weak name locality, or expensive cold
index walks can erase the benefit.

Immutable object-backed metadata already has strong
precedents~\cite{deltafs2021,cvmfs2011,nydus_rafs}. We will compare the joint
layout with immutable sorted-KV records at equal content and cache budgets,
and with compatible demand-loaded immutable-image systems. Standalone
read-only and workspace-lower use are separate comparisons. The sorted-KV
control tests layout organization and is not a reproduction of DeltaFS.
