\section{Packed Metadata}
\label{sec:packed}

A fixed collection requires no namespace updates, yet serving it through
the mutable catalog can consume the same query capacity as active
workspaces. Packed Metadata uses immutability to change this service
path. It organizes a directory version into authenticated object pages
from which readers obtain names, common attributes, and data locators.
Construction is paid per version; subsequent readers reuse the result.

\subsection{What is packed}

Packed Metadata applies to a selected read-only directory version that
has been explicitly built and published. It can serve a standalone
read-only mount or supply a workspace lower. Writes in the latter case
go to the private upper, leaving the published pages immutable.

A logical read group contains entries from one parent directory over
a range of raw names in byte order. Its joint metadata page co-locates
each entry with common attributes and data locators. A name lookup can
therefore supply information needed by subsequent attribute and data
operations from the same fetched page. During enumeration, a decoded
page supplies successive entries in its range. Section~\ref{sec:implementation}
describes the caches used by individual name queries.

Raw pages are bounded at 256 KiB. A physical container may hold several
groups, so the metadata access unit need not equal the stored object.
Range indexes route queries to groups; index height depends on page
capacity and record count rather than source-directory depth.

\subsection{Querying a pinned snapshot}

A reader pins a manifest and starts from its authenticated index roots.
For a name lookup, the directory-name index identifies the group covering
the key. The reader resolves the container and fetches the metadata page's
byte range. Before decoding, it verifies the stored-byte digest; after
decoding, it checks entry counts and name boundaries against the
authenticated group reference. The matching record supplies the inode,
common attributes, and data locator (Figure~\ref{fig:packed}).

Other queries use indexes suited to their keys. Attribute queries
addressed by inode use a separate index. Enumeration traverses ordered
name ranges, with counted indexes supporting directory-ordinal navigation.
A file read returns inline contents or follows a locator to an
authenticated descriptor and verified payload range. Packed data frames
define snapshot-level access and integrity units; the backend serves
them using its own persisted object layout.

Every returned record or payload must connect through authenticated
references to the pinned manifest. Missing objects and failed
authentication are errors, not evidence that a name is absent. Cached
records remain valid for that identity after newer versions appear.
A cold lookup may still require several index requests; data reads can
add descriptor and payload requests. Co-location provides opportunities
for reuse without fixing the number of GETs per operation.

Supported lower queries need no per-file record in the mutable database.
Private-upper checks, mutations, and ownership coordination continue
through the workspace and control services.

\subsection{Building and publishing a version}

Construction starts from a consistent source view, established by a
snapshot or validation protocol. This captures one directory version
before its records are reorganized. The producer groups records,
uploads objects, and builds the indexed manifest. Publication installs the binding after
the referenced objects are durable and valid. Retained versions and
readers keep their objects live until reclamation is safe.

If no published pack exists, the first packed fork additionally waits
for construction, upload, validation, and publication. A native overlay
requires native version capture and binding but avoids pack construction.
Later children reuse the published pack rather than rebuilding it. Query
offload can help while the original database records are retained;
reducing their persistent footprint also requires safe retirement, which
is a separate step from the offload itself.

The relevant cost therefore spans construction, each use, retention, and
reclamation. Grouping gives related queries a common page to reuse;
the available caches determine whether that reuse occurs. Isolated
lookups may transfer unused records. Inlining, compression, and payload co-packing
introduce additional effects that must be measured separately. Long
retention or rapid version churn can outweigh access savings even when
queries become faster.

Section~\ref{sec:evaluation} varies the number of readers, query locality,
and version lifetime to identify when reuse repays this preparation cost.
