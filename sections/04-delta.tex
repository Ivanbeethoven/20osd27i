\section{Delta-Based Workspaces}
\label{sec:delta}

\subsection{Creating a view and resolving names}

Creating a workspace gives a task the shared starting files and an
independent place to record changes. The workspace binds a shared
immutable lower $S$ and maintains a private writable upper $\Delta_i$,
with view $W_i=\operatorname{Resolve}(S,\Delta_i)$. A sealed catalog in the
metadata database and a packed snapshot on object storage can supply the
same inherited records through different access paths.

Creation registers the base identity and independent private state.
The catalog path identifies the base by its layer, sealed version, and
root hash; a packed lower additionally binds its authenticated manifest.
Unchanged entries and file contents remain reachable through this identity,
so creation need not copy the complete metadata tree. Binding validation,
ownership records, and mount preparation still contribute to its cost.

A name lookup first consults the private record, which distinguishes a
present entry, an explicit deletion, and absence. For parent directory
$d$ and name $n$, let $H_i(d,n)$ indicate that an applicable rule blocks
inheritance of that lower name. Then
\begin{equation}
R_i(d,n)=
\begin{cases}
e, & \Delta_i(d,n)=\operatorname{Present}(e),\\
\bot, & \Delta_i(d,n)=\operatorname{Whiteout},\\
\bot, & \Delta_i(d,n)=\operatorname{Absent}\land H_i(d,n),\\
R_S(d,n), & \Delta_i(d,n)=\operatorname{Absent}\land\neg H_i(d,n).
\end{cases}
\end{equation}
Here $\bot$ denotes an absent lookup result. A whiteout suppresses the
inherited name. $H_i$ covers applicable directory-opacity or other
lower-inheritance rules, not visibility of a present upper entry.
Absence permits fallback only when $H_i$ is false. Deleting an inherited
file must therefore preserve a deletion marker; merely removing a private
record could expose the lower file again.

Directory enumeration applies the same precedence to each name, removes
duplicates, and returns attributes of the visible inode. Private
attributes describe its current state rather than an arithmetic merge
with lower attributes. Materializing private inode state must preserve
the identity shared by hard-link aliases. Rename and other namespace
mutations must update related entries consistently within the workspace.

\subsection{Resolving overwrites and truncation}

An overwrite changes which bytes a file range references. The catalog
path records private data extents alongside namespace and inode changes.
The Entity path supplies one concrete current-state representation:
each changed logical chunk has a normalized map with explicit \emph{Data},
\emph{LowerRange}, and \emph{Hole} spans. Data references newly stored upper
bytes, LowerRange references inherited bytes in $S$, and Hole reads as
zeros. An explicit map must cover its applicable range completely;
an uncovered interval is not an implicit lower reference.

A short overwrite stores new bytes and replaces their mapped interval,
while unchanged intervals can retain lower references. This does not
require a byte-difference algorithm or copying the whole lower file.
Truncation must also prevent discarded lower bytes from reappearing.
Entity maintains a lower-visible size that can decrease but cannot
increase. Extending a truncated file exposes zeros or new upper data
beyond that boundary, rather than old bytes from $S$. Object formation
and integrity checking determine the stored units independently: a short
logical write need not produce an equally short object.

The VFS dirty overlay handles a separate read case: this client's bytes
are readable before writeback completes. If local dirty data covers
$[4,8)$ KiB, a read of $[2,10)$ KiB combines two committed 2 KiB ranges
with the dirty 4 KiB range. Workspace delta state instead determines
persistent namespace, attribute, and data-mapping visibility. A buffered
workspace path can use both mechanisms, but local read-your-writes
behavior alone establishes neither remote durability nor a published
recovery point.

\subsection{Publishing and retaining a version}

Publishing a new data mapping creates a dependency on its referenced
objects. The Entity path uploads an object durably before publishing its
mapping. The ordinary VFS offers upload-before-commit and explicitly
selected commit-before-upload modes; the latter can expose a mapping
before its object is remotely available. Preparing a recoverable version
therefore requires an explicit drain and validation boundary, even when
local reads already return new data.

A recoverable worker handoff requires application checkpoints and a stop
to new source writes. Required payloads and metadata must become durable
and validated before an immutable version reference is published. The
destination then binds that version and acquires authority for subsequent
private writes. Lease and generation checks must reject stale writers.
This protocol must establish a file recovery point; the application
runtime is responsible for restoring sessions, restarting tools, and
reopening files. The file version does not transfer running processes
or guarantee recovery of progress beyond the last confirmed publication.
Section~\ref{sec:implementation} distinguishes the available publication
and recovery paths.

A published baseline must remain available for every workspace or reader
that still holds it. Publishing a replacement must not invalidate those
readers, and reclamation must separate live references from abandoned
construction objects. This lifetime requirement applies to either lower
representation. For one shared baseline, live logical metadata obeys
\begin{equation}
M_{\mathrm{live\text{-}meta}}=M_S+\sum_i M_{\Delta_i}+M_{\mathrm{control}}.
\end{equation}
$M_S$ counts the shared metadata once; $M_{\Delta_i}$ counts private names,
attributes, deletion records, and mappings; $M_{\mathrm{control}}$ counts
disjoint binding and ownership records. Upper payload, encoding and
checksum overhead, unreclaimed objects, and caches belong to separate
physical accounting. Private state includes complete current records
and mapping overhead, so its cost grows with modification and deletion.
The evaluation will compare this cost with materialized workspaces under
matched visibility and durability contracts.
