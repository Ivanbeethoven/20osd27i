\section{Delta-Based Workspaces}
\label{sec:delta}

\subsection{A shared baseline and private changes}

The unit of private state determines the cost of an isolated edit.
Copying a namespace at fork repeats its metadata; copying an inherited
file on its first write can materialize bytes the attempt never changes.
Delta-based workspaces instead retain private records for changed names,
attributes, deletion markers, and data ranges over a shared immutable
baseline. The baseline keeps inherited references stable, while private
records describe the current visible state.

Workspace creation registers the immutable base and the private control
state without copying the metadata tree. The catalog identifies the base
by layer, sealed version, and root hash; a packed lower also binds its
authenticated manifest. Creation validates this binding, registers
ownership, and prepares the mount. The lower can use native
metadata or an already published pack (Section~\ref{sec:packed}).

\subsection{Resolving names}

Lookup first checks the private upper. An entry supplies the result;
a deletion marker reports absence and stops the lookup. Otherwise, the
reader consults the lower unless an opaque directory or another
inheritance rule hides the name. Those rules suppress inherited entries,
leaving explicit upper entries visible. Deleting an inherited name must
retain its marker, since removing the upper record alone would expose
the lower name again.

Directory enumeration applies the same precedence and removes duplicate
names. Both the buffered and direct-I/O workspace paths preserve an
inherited file's inode number when materializing private attributes or
mappings. Updates through one hard-link alias therefore remain visible
through the others.

Rename must change the source and destination bindings together.
The direct-I/O path locks participating inodes in number order, validates
the observed records and writer authority, and commits the source
deletion marker, destination binding, and affected inode and parent
records in one transaction. Namespace reads validate an operation-local
view and retry conflicts, preventing a partially applied rename from
becoming visible within an operation. Section~\ref{sec:implementation}
describes the buffered path and the scope of these guarantees.

\subsection{Overwrites and truncation}

An overwrite changes the data references for a file range. The buffered
path records private extents alongside namespace and inode changes.
The direct-I/O path represents each changed logical chunk with a
normalized map of upper data, lower references, and zero-filled holes.
Within the range a map covers, every interval names exactly one source,
which makes the visible source unambiguous. Ranges without a private
override inherit the lower's bytes up to the lower-visible boundary.
This boundary only shrinks as the workspace truncates inherited data.

A short overwrite replaces its interval and retains lower references
elsewhere. Truncation must invalidate both inherited and previously
written bytes. The direct-I/O path first commits the reduced size,
a nonincreasing lower-visible boundary, and a cleanup intent. Cleanup
replaces discarded spans with zeros; extension completes pending cleanup
before increasing the size. For example, after an overwrite of
6--10 KiB, truncation to 7 KiB, and extension to 12 KiB, the range
7--12 KiB must read as zeros. Reducing only the inherited boundary
would leave the discarded upper bytes available to a later extension.

\subsection{Publication and retention}

The direct-I/O path uploads an object durably before publishing its
mapping. Ordinary buffered writeback also defaults to upload-before-commit,
but offers an explicit commit-before-upload mode. That mode can expose
mappings before their objects are remotely available. Preparing a
recoverable version must therefore drain and validate referenced objects,
even when local reads already return the new data.

Worker handoff requires stopping source writes and making payloads and
metadata durable before publishing the version. The destination binds
that version and acquires write authority; lease and generation checks
must reject stale writers. Applications checkpoint execution state
and reopen files separately, because a published file version carries
file contents and names, not process memory or open handles.

Reclamation retains every object still referenced by a workspace or
reader and distinguishes these objects from abandoned construction output.
Private metadata grows with modifications and deletion markers; retained
baselines and ownership records contribute shared overhead. The evaluation
accounts for both live references and objects awaiting reclamation.
