\section{Background and Motivation}
\label{sec:motivation}

\subsection{The ordinary file-system path}

Tools issue file operations through FUSE. The file system resolves names and
attributes through its metadata path, translates file offsets through data
mappings, and obtains payload bytes from local caches or object storage.
Writes introduce new data and update those mappings under the selected
visibility and durability protocol. This ordinary path is useful without
shared workspaces, packed snapshots, or backend layout hints.

A workspace can contain source files, dependency directories, generated
artifacts, build trees, and temporary files. Some subtrees remain stable across
tasks; others are frequently rewritten. A deployment can choose stable state
as a shared baseline while retaining private changes for each task. The
usefulness of doing so depends on cross-task overlap, mutation footprint,
and baseline lifetime. Agent framework papers establish that repository
navigation and editing occur; they do not establish that every task shares
most of its state or benefits from a layered view.

\subsection{View sharing and metadata access are separate choices}

A shared view needs a stable identity and rules for resolving private changes.
It does not prescribe how baseline records are stored. A native catalog or
KV namespace can supply the same immutable names and attributes as an
object-resident packed representation, provided each satisfies the view's
lookup contract. Conversely, a read-only consumer can use packed metadata
without allocating a writable workspace.

Metadata organization and caching already reduce service costs in TableFS,
IndexFS, LocoFS, and InfiniFS~\cite{tablefs2013,indexfs2014,locofs2017,infinifs2022}.
It would be misleading to assume that every operation on native metadata
requires a separate network round trip. Packing exploits a more specific
property: records that cannot change after publication can be indexed and
fetched together without joining the mutable update protocol. A directory
scan may reuse names, attributes, and data locators from one fetched page;
a random point lookup may consume only a small part of that page.

The relevant property is \emph{lower-query independence}: supported baseline
queries can obtain their records from the snapshot objects. Mutable upper
records, reader pins, publication, and reclamation may still use a metadata
service. DeltaFS's private logs and selectively assembled namespaces likewise
show why namespace sharing must be compared with more than one global mutable
metadata design~\cite{deltafs2021}. Equal cache budgets and appropriate batch
access belong in these comparisons.

\subsection{Object formation and physical work have different boundaries}

An application's request size, a logical chunk, the client block size $g$,
and the finalized object length $L_o$ describe different stages. A chunk
provides an addressing range; slice mappings describe visible file data;
blocks determine how a slice becomes objects. Tail blocks, compression,
and framing can make $L_o$ differ from $g$. An object format and the client's
cache and verification policy then determine whether a read fetches a range
or an entire object.

Backend coding adds further boundaries. An erasure-coding block of size $B$
is distributed across data and parity shards. The physical verification/read
quantum $q$ determines the verified units required within the serving shards.
Storage systems already make different choices about striping, coding, and
redundancy transitions~\cite{azureec2012,morph2024,okapi2025}. A compatible
backend can expose an additional layout choice without changing the file
system's view semantics or the client's object boundaries.

These distinctions motivate separate measurements of requests, network
bytes, physical bytes, CPU work, and durable write completion. A smaller $g$
can increase request count; a smaller $q$ adds checksums and processing;
a fixed data/parity ratio retains its nominal redundancy. Caches and
whole-object verification can hide a physical-layout benefit. The evaluation
must trace actual object formation and reads rather than infer storage work
directly from a FUSE request histogram.
