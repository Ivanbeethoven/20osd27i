\section{Background and Motivation}
\label{sec:motivation}

\subsection{Private work and shared inputs}

An agent's workspace contains source files, dependencies, generated
artifacts, and temporary files. Two attempts starting from the same
revision may read the same file and then make incompatible edits.
Each must continue to see its own version, including after deletion
or truncation. A stable baseline identity and private changes provide
this isolation independently of where metadata and bytes reside.

Read-only inputs have a different lifetime from working state. In the
machine-learning scenario, an experiment reads a fixed dataset while
writing model checkpoints and transformed outputs elsewhere. A
directory-based image loader, for example, enumerates a dataset to
build a sample list, then opens selected files during
loading~\cite{torchvision_folder}. Separate experiments repeat this
discovery work against the same version, so the namespace of that
dataset is read repeatedly while the data itself never changes.

Two properties make such a collection different from ordinary working
state. Its content is fixed for the lifetime of a version, so its
records can be organized once and reused by every reader. And its
metadata occupies a larger fraction of its representation: every file
requires a name, attributes, and a data locator regardless of its
payload length.

\subsection{From file operations to storage work}

Reading a file requires path resolution, a data mapping, and access
to the referenced bytes. Metadata services batch and cache
records~\cite{tablefs2013,indexfs2014}, while immutable distributions
organize them for demand fetching~\cite{cvmfs2011,nydus_rafs}. A
file-system call therefore need not cause a remote metadata request.
The relevant question is how much database traffic remains under the
actual cache and concurrency conditions.

Payload access introduces another translation. Kernel caching and
readahead determine which requests reach FUSE; the client then fetches
object ranges or complete objects. Encoding and integrity checks may
require still larger physical reads~\cite{azureec2012,okapi2025}. Writes
pass through buffering and object formation before publication. FUSE
request lengths thus describe neither application syscall sizes nor
physical storage units, and a mechanism that changes one layer does not
by itself change the others.

\subsection{Design implications}

The coding traces supply the access shape that the mechanisms must
fit: many metadata calls, mixed request lengths, and bursts of activity
within a task. Baseline reuse is a separate workload assumption:
attempts that start from the same tree and modify a small part can
retain references to unchanged state. The traces do not measure that
sharing or modification pattern.

The machine-learning scenario adds a complementary case: a fixed
collection of many small files, read repeatedly by many consumers,
whose namespace should not compete with the mutable updates of the
writers that use it. Together they point to three separable cost
reductions, and Section~\ref{sec:overview} describes how \sys keeps
workspace state, metadata representation, and payload layout apart so
that each can be chosen on its own terms.
