\section{Background and Motivation}
\label{sec:motivation}

\subsection{Private work and shared inputs}

An agent's workspace contains source files, dependencies, generated
artifacts, and temporary files. Two attempts starting from the same
revision may read the same file and then make incompatible edits.
Each must continue to see its own version, including after deletion
or truncation. A stable baseline identity and private changes provide
this isolation independently of where metadata and bytes reside.

Read-only inputs have a different lifetime from working state. In the ML
scenario, an experiment reads a fixed dataset while writing model
checkpoints and transformed outputs elsewhere. A directory-based image
loader, for example, enumerates a dataset to build a sample list, then
opens selected files during loading~\cite{torchvision_folder}. Separate
experiments can repeat this discovery work against the same version.

Only a selected, already packed directory benefits from Packed Metadata.
New files and in-place updates are outside that immutable version;
revised data requires publication of a new version. A private upper can
hold workspace changes without modifying the packed lower. Small-file
collections are a particular target because they require many names,
attributes, and data locators relative to their payload size. Datasets
stored in a few large shards offer less of this opportunity.

\subsection{From file operations to storage work}

Reading a file requires path resolution, a data mapping, and access
to the referenced bytes. Metadata services batch and cache
records~\cite{tablefs2013,indexfs2014}, while immutable distributions
organize them for demand fetching~\cite{cvmfs2011,nydus_rafs}. A
file-system call therefore need not cause a remote metadata request.
The relevant question is how much database traffic remains under the
actual cache and concurrency conditions.

For a fixed small-file collection, object-resident metadata can move read
service away from the database handling mutable updates. Construction
and publication must be amortized over the version's uses. The likely
gain also depends on locality: neighboring queries can share a metadata
page, whereas scattered queries may fetch records they never use.

Payload access introduces another translation. Kernel caching and
readahead determine which requests reach FUSE; the client then fetches
object ranges or complete objects. Encoding and integrity checks may
require still larger physical reads~\cite{azureec2012,okapi2025}. Writes
pass through buffering and object formation before publication. FUSE
request lengths thus describe neither application syscall sizes nor
physical storage units.

\subsection{Design implications}

The coding traces motivate positive and negative metadata queries,
mixed request lengths, and bursty replay. The ML scenario adds a
complementary question: can repeated access to a fixed small-file
dataset repay packing and reduce interference with mutable work?
Both require measuring the work induced below the file-system interface.
Section~\ref{sec:overview} describes how \sys separates workspace state,
metadata representation, and payload layout to make these costs explicit.
