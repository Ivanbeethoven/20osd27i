\section{Implementation}
\label{sec:implementation}

\sys connects the mechanisms through buffered, direct-I/O, and standalone
read-only paths. Their cache, publication, and recovery behavior differs.
The following describes the inspected implementation; runtime and failure
validation is included in the evaluation plan.

\subsection{Access paths}

An ordinary volume resolves mutable metadata and uses buffered caching
and writeback. A workspace can reuse that path with private-state
resolution over a sealed catalog or packed lower. A standalone packed
reader serves read-only access without a private upper. Its metadata
cache is separate from payload caching; configurable payload-cache and
prefetch budgets are not currently admitted on this path.

The packed reader caches index pages, resolved names (including absence),
and attributes. An uncached name still fetches and decodes its joint
metadata page. Reusing decoded pages across different names remains
an optimization opportunity; the current result caches do not establish
that benefit.

The direct-I/O workspace stores private namespace and mapping records
transactionally. It implements the rename and truncation protocols in
Section~\ref{sec:delta}, bypassing buffered writeback and metadata
time-to-live caching. Admission bounds limit operation sizes,
complete-directory enumeration, and the live ownership set. This path
currently supports newly created workspaces without process-crash takeover.

Direct reads authenticate an entire upper object before returning a
subrange. A smaller backend verification unit may therefore leave
short-read work unchanged. Comparisons with buffered volumes must
account for this fetch policy as well as the different caches.

\subsection{Publication and recovery}

Snapshot publication validates uploaded objects before installing the
lower binding and acquiring reader ownership. Recovery also checks
generations and leases; a manifest identity alone conveys no write
authority. The connected recovery path reuses the same persistent
storage allocation and checks worker identity and scoped metadata
authority. Arbitrary-worker migration still requires orchestration.

Catalog lifecycle operations support quiescence, object verification,
retention, and atomic version transitions. A runtime must connect these
operations to handoff, checkpoint execution state, and reopen tools.
The recoverable storage state is a published file version.

\subsection{Layout support}

The ordinary uploader defaults to $g=4\MiB$ within 64 MiB chunks,
and readers use the same geometry. Incompatible configurations are
rejected. The proposed 1/4/8/16 MiB settings are fixed configurations.

Backend hints require compatible client and server support. Hint
admission and new verification framing have separate enable and
fleet-compatibility gates, both disabled by default. Effective layouts
are persisted for later reads and repair; changing settings does not
re-encode existing objects.

The ordinary uploader propagates hints. Direct workspace writes and the
current snapshot producer use defaults; extending them must preserve
conditional object creation and conflict rejection. Direct workspace
objects contain write fragments, capped at the automatic policy's
no-hint threshold, rather than ordinary buffered blocks.

The current policy omits hints for $L_o\leq1\MiB$ and requests
$B=1\MiB$ otherwise. The inspected backend already defaults to
$B=1\MiB$, so enabling the policy can leave stored geometry unchanged.
It can nevertheless change client fetch and cache behavior. Experiments
must inspect actual $(g,L_o,B,q)$ and separate these client effects
from changes in physical layout.
