\section{Implementation}
\label{sec:implementation}

\sys implements the representations through buffered workspaces,
direct-I/O workspaces, and standalone read-only mounts. Their cache,
writeback, and recovery policies determine which operations and
performance effects the evaluation can compare.

\subsection{Access paths}

Ordinary volumes use mutable metadata and buffered writeback.
Buffered workspaces add private-state resolution over a sealed catalog
or packed lower. They serialize local mutations and use version-guarded
catalog transactions. Dirty buffers satisfy local reads before writeback;
recovery additionally requires the referenced data to become durable.
Standalone packed mounts omit the private upper and currently require
zero payload-cache and prefetch budgets.

The authenticated packed reader caches index pages, per-name results
including absence, and attributes. Directory enumeration retains and
reuses the decoded joint page for its current group. Independent name
lookups fetch and decode that page on a per-name cache miss; decoded-page
reuse across those queries is not implemented.

Direct-I/O workspaces store private namespace and mapping records
transactionally, implementing the rename and truncation rules in
Section~\ref{sec:delta}. Namespace protocols on both paths are scoped
to individual operations; separate calls can observe different committed
versions. Direct-I/O workspaces bypass buffered writeback and metadata
time-to-live caching, with admission bounds on operation sizes,
enumeration, and ownership. This path supports fresh workspaces without
process-crash takeover. It authenticates an entire upper object before
returning a subrange, so smaller backend verification units do not
reduce the bytes this client fetches.

\subsection{Publication and recovery}

Publication validates durable objects before installing a lower binding
and acquiring reader ownership. Recovery checks generations and leases;
a manifest identity alone conveys no write authority. The connected
recovery path reuses the same storage allocation and checks worker
identity and scoped metadata authority. Catalog operations provide
quiescence, verification, retention, and atomic version transitions.
Cross-worker handoff requires runtime orchestration to connect them to
session checkpoints and tool reopening.

\subsection{Layout support}

The ordinary uploader defaults to $g=4\MiB$ within 64 MiB chunks.
Readers use the same geometry; incompatible configurations are rejected.
The RustFS extension accepts explicit coding-block-size hints of
64 KiB, 256 KiB, 1 MiB, and 4 MiB. Hint admission and new verification
framing have separate rollout gates requiring deployment-wide
compatibility confirmation. The ordinary uploader passes hints;
direct workspace writes and the snapshot producer use defaults.
Existing objects retain their stored layout after configuration changes.

The current automatic policy omits hints for $L_o\leq1\MiB$ and
requests $B=1\MiB$ otherwise. RustFS's default coding-block size is also
1 MiB, so this policy can leave geometry unchanged. Enabling hints also
changes the ordinary client's fetch and cache policy. The evaluation
therefore records actual $(g,L_o,B,q)$ and holds the client policy fixed
when isolating the effect of a backend layout change.
