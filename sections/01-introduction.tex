\section{Introduction}
\label{sec:intro}

Agent services run several attempts from the same source revision,
dependency tree, or dataset. Each attempt reads shared inputs, makes
private edits, and produces artifacts that later attempts may reuse.
Coding agents exercise this pattern through repository exploration,
builds, and tests~\cite{sweagent2024,openhands2025}. An attempt may also
continue on another worker, requiring its saved files to remain
accessible after the original container exits. The file system must
therefore support both isolated modification and repeated access to
shared state throughout execution.

Sharing file contents addresses only part of this cost. Materializing
a private namespace for every attempt repeats metadata work even when
the payloads are shared. Copy-on-write overlays avoid that initial copy,
but their update granularity determines how much inherited state a
small edit materializes. OverlayFS and BranchFS establish the utility
of private upper layers~\cite{overlayfs,branchfs2026}; the remaining
question is how to represent name and byte-range changes while retaining
references to the rest of a distributed baseline.

Shared inputs introduce a separate access cost. Consider ML experiments
that reuse a fixed training dataset while writing different code,
checkpoints, and outputs~\cite{mlebench2025}. For a collection of many
small files, each run may enumerate the same directories and request
the same attributes from the catalog that handles workspace updates.
Exporting metadata for recovery leaves that lookup path unchanged.
Immutable distribution systems show how to serve a fixed tree through
an index~\cite{cvmfs2011,nydus_rafs,cofs2026}. For a training dataset,
the design question is which records a lookup should fetch together and
how many runs will reuse the published version before the dataset changes.

The bytes returned by those lookups introduce a third cost. A small
file read may fetch a larger client object, and the object store may
read and verify still larger shard intervals. Small objects reduce
the amount fetched by whole-object readers but increase object count
and request overhead. Backend encoding and integrity checks impose
their own units. Controlling this work requires an interface between
file-system object formation and the object store's physical layout.

We present \sys, an object-backed distributed file system that separates
private workspace state, read-only metadata representation, and payload
layout. A shared baseline fixes what a reader inherits; the representations
of private changes, metadata, and objects determine the work required
to serve that view. \sys implements three mechanisms:

\begin{itemize}
\item \textbf{Delta-Based Workspaces} retain private namespace records
and data-range mappings over a pinned immutable baseline. An edit
replaces the affected mappings while unchanged ranges retain their
references. Deletion and truncation rules prevent discarded state from
reappearing (Section~\ref{sec:delta}).
\item \textbf{Packed Metadata} partitions a fixed directory version
by parent and name range. Each page holds names, common attributes,
and data locators. Once the version is published, readers can resolve
a name from its authenticated page in object storage or cache without
querying the mutable catalog for that entry (Section~\ref{sec:packed}).
\item \textbf{Variable-Granularity Object Storage} separates client
object formation from backend encoding and verification. We co-design
the interface with RustFS: \sys can attach a coding-block-size hint to
a finalized object, and our RustFS extension validates the hint and
persists the effective layout for reads and repair
(Section~\ref{sec:layout}).
\end{itemize}

The mechanisms are independently optional. A native-metadata workspace
can fork without constructing a pack; a published pack can serve
standalone read-only access; an ordinary volume can use the layout
interface. This choice matters because their costs differ. Packing
introduces a per-version preparation cost, while finer object and
verification units trade reduced over-read for more requests and
checksums. The appropriate configuration depends on the state being
shared and how it is accessed.

We implement these mechanisms and characterize 1,138,884 FUSE requests
from eight coding-agent runs. Metadata methods account for 57.3\% of
the requests, with mixed read/write lengths and concentrated bursts
of activity (Figure~\ref{fig:agent-fuse-combined}). These observations
define access patterns for evaluation. Section~\ref{sec:evaluation}
sets out the controlled comparisons for mechanism costs, fork, worker
handoff, and concurrent execution.
