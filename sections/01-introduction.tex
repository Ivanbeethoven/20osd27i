\section{Introduction}
\label{sec:intro}

Coding agents work through ordinary file-system tools: they traverse a
repository, inspect source files, edit code, and run builds and
tests~\cite{sweagent2024,openhands2025}. Consider a service that launches
several attempts from the same repository revision and dependency set.
Each attempt needs a consistent starting view and independent changes.
Serving it requires both provisioning that view and resolving names,
attributes, and file data throughout execution.

Sharing a baseline addresses provisioning, but leaves these access costs
open. Layered namespaces and copy-on-write branches already let tasks reuse
state while keeping changes private~\cite{overlayfs,branchfs2026,deltafs2021}.
Immutable distributions provide indexed, demand-loaded
state~\cite{cvmfs2011,nydus_rafs}. A mature immutable lower with a compatible
writable upper and object backend is therefore a strong direct alternative.
Any comparison with this composition must include its sharing and caching.
The remaining
question is how the metadata and object units fetched by a task affect
request count, transferred bytes, and processing work.

We reanalyzed 1,138,884 FUSE requests from eight coding-agent task runs
(Section~\ref{sec:agent-observations}). Metadata operations, including
unsuccessful probes, made up more than half of the requests in each of the
two workload groups. Reads and writes had mixed request lengths, and
activity varied substantially across tasks and over time. These observations
motivate examining access costs alongside provisioning; request counts alone
do not identify a latency bottleneck or establish cross-task reuse.

Our design separates the state a task shares from the units used to access
that state. A workspace resolves private changes before querying its pinned
lower version; lower answers need not depend on one metadata representation.
Data locators connect those answers to object ranges, whose interpretation
must preserve the referenced bytes across storage layouts. These interfaces
allow different access units to serve the same logical file view. Our
hypothesis is that separating shared-version identity from metadata and
object access units can reduce lifecycle storage work under matched
visibility and durability contracts. The expected savings
depend on unchanged-state reuse, metadata locality, or selective data access,
and must exceed construction and maintenance costs. Direct composition may
already capture those savings; matching or exceeding its cost would weaken
the case for the corresponding mechanism.

\sys realizes this design in an object-backed file system with three
mechanisms. \emph{Delta-Based Workspaces} resolve a shared immutable
baseline with private namespace and data-mapping changes. \emph{Packed
Metadata} groups immutable names, attributes, and data locators into indexed
pages on object storage, moving fixed-version queries away from the central
metadata database while mutable and control records remain there.
\emph{Variable-Granularity Object Storage} separates
client object formation from optional backend encoding and verification
units. Each addresses a different cost and remains optional: workspaces
can use native metadata, packed snapshots can serve read-only mounts, and
ordinary volumes can configure object granularity. Section~\ref{sec:overview}
defines their composition interfaces.

The paper develops private-view resolution, immutable metadata lookup and
publication, and file-to-object access rules. It connects those rules to
the inspected implementation (Section~\ref{sec:implementation}) and the
completed request-characterization study. System performance and failure
experiments remain planned (Section~\ref{sec:evaluation}); neither the
observations nor source inspection establishes a system speedup.
