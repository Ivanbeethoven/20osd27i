\section{Introduction}
\label{sec:intro}

Coding agents traverse repositories, inspect files, edit code, and run
builds and tests~\cite{sweagent2024,openhands2025}. When a service launches
several attempts from the same revision, each needs a consistent starting
view and private changes. Saved results must remain available for later
attempts or another worker. Storage must provide these views while serving
their names, attributes, and file data throughout execution.

Machine-learning (ML) agents also prepare datasets, train models, and
compare experiments~\cite{mlebench2025}. Consider several such agents
exploring models against one fixed training dataset. Their code,
checkpoints, and temporary outputs differ, while the input data remains
read-only. If the dataset contains many small files, sharing its bytes
still leaves a large namespace to serve. This case motivates a selective
optimization: pack the stable data directory once and reuse its metadata
across experiments, while keeping mutable working state outside the pack.

Prior systems provide much of the foundation. OverlayFS and BranchFS
isolate private changes over shared state~\cite{overlayfs,branchfs2026};
DeltaFS publishes private namespace updates as immutable
logs~\cite{deltafs2021}. IndexFS and InfiniFS improve metadata organization,
distribution, and caching~\cite{indexfs2014,infinifs2022}. CernVM-FS and
Nydus serve immutable file trees with indexed metadata and on-demand
data access~\cite{cvmfs2011,nydus_rafs}. CoFS exploits a fixed image
namespace to index metadata for kernel lookup~\cite{cofs2026}.
Building on these approaches, an object-backed workspace must decide how to represent private
updates, which fixed metadata to serve outside the mutable database,
and which units to fetch and verify.

These decisions incur different costs. In a database-backed file system,
queries over fixed collections can compete with active namespace
updates~\cite{juicefs_architecture}. Packing redirects supported queries
to object storage and client caches, at the cost of constructing and
publishing a version. A native overlay can fork without that additional
work. Separately, object formation and backend layout determine how much
storage work a partial read requires. Reducing fork cost therefore does
not necessarily reduce the cost of using the resulting workspace.

Our workload study reinforces the need to examine access as well as
creation. Across 1,138,884 FUSE requests from eight coding-agent runs,
metadata methods accounted for 57.3\% of all calls.
Requests also varied in length and arrived in bursts
(Section~\ref{sec:agent-observations}). These observations characterize
coding workloads; they do not measure ML data access or establish
a metadata-service bottleneck.

\sys separates the identity of shared state from its metadata
representation and payload access units. Three mechanisms implement
this separation:

\begin{itemize}
\item \textbf{Delta-Based Workspaces} retain private namespace state and
data-range mappings over a pinned baseline. Unlike file-level copy-up
in the BranchFS prototype, unchanged ranges keep their original
references. The lower-query interface accepts native or packed metadata
(Section~\ref{sec:delta}).
\item \textbf{Packed Metadata} serves an explicitly packed read-only
subtree through authenticated object pages. Directory-name groups
co-locate entries, common attributes, and data locators for reuse across
related operations. Fixed-version queries leave the per-file database
path; mutable updates and lifetime control remain in their existing
services (Section~\ref{sec:packed}).
\item \textbf{Variable-Granularity Object Storage} separates client
object formation from backend encoding and verification. A finalized
object can carry a layout hint, which the backend validates and persists
for subsequent reads and repair (Section~\ref{sec:layout}).
\end{itemize}

Each mechanism can be used independently. A workspace can retain native
metadata; a packed dataset can serve standalone read-only access; an
ordinary volume can configure object granularity. Packing is most
plausible for stable, metadata-intensive collections reused across many
readers. Frequent updates or little reuse may leave native metadata
cheaper, while smaller storage units can add requests and checksums.

This paper presents the design, implementation, and completed workload
characterization. The evaluation plan isolates the three mechanisms
before examining fork, migration, and concurrent execution
(Section~\ref{sec:evaluation}).
